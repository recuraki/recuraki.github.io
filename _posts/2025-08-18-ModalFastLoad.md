# [コンテナロードの高速化 - Fast, lazy container loading in Modal.com](https://modal.com/blog/jono-containers-talk)

Modalはコンテナ型のプラットフォームである。ところで、LLMの学習などではこのコンテナのイメージサイズが問題になることがある。コンテナは起動時に「イメージ」をロードする。例えば、Bert推論をするイメージは8GBくらいあるのでこの読み込みが問題になる。

まず、コンテナロードの問題を考えると、eager(積極的)とlazy(遅延的)なアプローチがある。

積極的なロードはDockerやk8sで使われるアプローチでN個の圧縮されたイメージからなっており、これらを全てダウンロードしておき、解凍するという手順になっているため、大きなサイズだと1分以上の展開コストがかかることがある。
Dockerやk8sはそもそも更新頻度が高くない前提のためこのアプローチが用いられる。

遅延アプローチはModalやAWS Lambdaで使われるアプローチでこれとは違い、もっと小さなチャンク（インデックス）として動作する。一つのインデックスは5MB程度であり、msオーダでロードができる。システム上ではこれらはなんらかのポインタとして指定されている。
ただし、ここでのインデックスとはデータ本体ではなくてメタデータである。実際のデータはURIでアクセス可能なBLOBストレージに保管されている。これらはホストのストレージ・メモリにもキャッシュされているので頻繁に使われる実データはキャッシュされている。
ここでのBLOBサーバとはS3のようなシステムであることがあるので、大きな空間でBLOBに保存されているデータへのアクセスは起動に数時間かかることだってあり得る。

この時にキャッシュは多くのユーザで共有されうることにも注目すべきである。例えは`AI/MLでよく使われるPython 3.11とそのライブラリ群` というのはページキャッシュされていれば多くのユーザがそれらを使うことができ、BLOBにはアクセスしないだろう。また、これは経験則だが圧縮して8GBになるようなデータはすべてのデータがアクセスされるわけではない。また、イメージが不要なデータにアクセスをなるべくしないような工夫が可能であるなら工夫すべきである。

この理由のため、オンプレホストはなるべく大きいべきである。小さなホストをたくさん立ち上げるとそのキャッシュ（例えばメモリ）の情報は分散してしまう。クラウド上のオンプレホストは帯域を分け合うことも注意すべきで、n台のホストで多量のデータを受信するならば1台のホストで受け取った方が高速なオリジンからの転送が完了する。
なお、我々の細かいTIPSとしてはSSDはRAID0にしておいた方が良い。少しでも各種スループットは早くすべきである。

もちろん、先読みを行う。つまり、あるチャンクが呼ばれた後にその次のチャンクを先に読んでおく。ただし、この先読みは32MB程度が我々の経験では良い。1GBなど大きな先読みをするとうまくOS側が動作しなかった。

# [メモリスナップショット - Memory Snapshots: Checkpoint/Restore for Sub-second Startup](https://modal.com/blog/mem-snapshots)

ModalとはサーバレスGPUコンテナランタイムです。そのFunctionを処理するノードが生存していればリクエストはそのノードで処理されますが、あるいは、ロードバランスの為、ワーカーノードが増えることもあります。この際にインスタンスの起動(`コールドブート`)は少しでも早いことが望まれます。`CPUスナップショット(メモリスナップショット)`はこの問題を大きく解決し最大で50%以上の起動時間短縮を実現します。

メモリスナップショットとはModal上でユーザの入力を受け付ける直前の状態を記録したスナップショットです。なお、メモリスナップショットだけでは(後述する)GPUのメモリスナップショットは含まれません。

`CRIU: Checkpoint/Restore in Userspace）`がこのスナップショット機能の原型です。GRIUはロシアで開発されたサーバレス環境のコールドスタートを短縮するための手法です。CRIUはコンテナ技術`runc`ランタイム向けに開発されていますが、modalではセキュリティ上の関係から`runsc`を用いています。
このため、メインストリームであるrunc向けのCRIUよりも少し遅れてrunsc向けのスナップショットは開発されてきました。

ところで、メモリのスナップショットでなぜ起動がそこまで高速に動作するのでしょうか？それはPythonのimportとはファイルシステムベースの動作で、多数の依存関係をimportするため、例えばtorchのimport1つで26,000回ものシステムコールがよばれているためです。先ほどの記事で説明した通り、ModalのFSはオンラインストレージを活用したFUSEで実装されています。このため、このアクセスのオーバーヘッドは無視できません。

この処理が完了した後のメモリの状態を保存しておけば、数万のシステムコールではなくてたった1つのファイル読み出しだけでユーザからの入力を受け付けられる状態にできるのです。

とはいえ、メモリのスナップショットは数Gに及ぶため、それを愚直に復元することは（その数Gを転送するために）オーバーヘッドがかかります。そこで、先読みをしたり、先に述べたチャンク的な横見込みを行うことでアクセスを高速にできるように試みます。

とはいえ、メインメモリの全てをディスクからメモリに書き戻すという操作にはその速度に律速された限界があります。コンテナを復元しようとするということは数GBのメモリを復元するということなので、数万回のファイルアクセスが発生します。ただし、これら全てが一定の速度で復元できるとは限らず、ロングテールなアクセス時間（ごく稀な長いアクセス待ち）を引いてしまうとメモリが復元できないのです。




# [GPUスナップショット - GPU Memory Snapshots: Supercharging Sub-second Startup](https://modal.com/blog/gpu-mem-snapshots)

ここまでに説明した通り、Modalではコールドスタートのレイテンシ削減に取り組んでいます。ModalはGPUの推論などに使われることも多く、このために、`GPUメモリスナップショット`の機能に対応します。

この機能はファイルシステムの工夫およびCPUメモリスナップショットに加えて実装されている機能です。これらの機能はコールドスタートの高速化に大きく寄与しており、だいたい3-5倍程度コールドスタートを高速化しています。

ここでModal関数をもう一度おさらいします。最初のステップはコールドブートで次のステップが入力の処理です。
`コールドブート`はプログラムをメモリまで読み込む処理です。この処理は関数の読み出しからするとあまり楽観視できる時間ではなく、例えば大きな画像ファイルを複数ファイルシステムにダウンロードしてからメモリに転送し、そのあと入力が可能になる、というプロセスには数秒（以上）かかることがあります。

このために前述したように`CPUメモリスナップショット`が導入されました(2025/1)。プログラムの入力待ちになる直前の状態をメモリスナップショットとておき、このメモリの状態を分散ファイルシステムにキャッシュするのです。関数が呼び出された時はここから起動をします。

ところが、GPUが主に使われる関数ではこれは満足なコールドスタートを実現しません。CPUメモリスナップショットはGPUのメモリ空間を含められない、という制約があるからです。CPUメモリスナップショットの記事で触れた通り、GPUを含まないメモリを復元したあと、NVIDIAのCUDA初期化シーケンスを走らせる必要があったのです。

とはいえ、何もスナップショットを行わない状態に比べてGPUに転送するメモリをCPU側でスナップショットできているわけですからGPU関数でもコールドスタートの期間を短縮することができました。とはいえ、CPU側に実際のGPUのメモリがそのまま記録されているわけでなく、CPUではGPUの種類に合わせて`コンパイル(torch.compike)`した後にGPUメモリに転送していました。そこでGPUメモリスナップショットは、コンパイルしてGPUメモリに転送されたメモリをスナップショットすることにしたのです。

この`CUDAチェックポイントとリストア`の機能は最近のリリース(570/575ブランチのドライバ)でサポートできるようになりました。このAPIは以下のようなCUDA状態を保存して復元できます。`GPU VRAM`, `CUDAカーネル`, `ストリームやコンテキストなどのCUDAオブジェクト`, `メモリマッピングの情報`などをこの機能で保存できるのです。

このチェックポイントの処理はCPUのチェックポイントに非常ににており、チェックポイントの作成がリクエストされるとCUDAプロセスをロックした上で、チェックポイントの処理を行います。つまり、ActiveにCUDAメモリを書き換えるプロセスを排除しておき、その状態を保存するのです。同時にCPUメモリの状態を保存します。

このようなアプローチによってGPUを用いるワークロードの起動は10倍ほど高層化するものもありました。特にLLM系のワークロードへの効果は絶大で`Qwen2.5-0.5B-Instruct`では45秒かかっていたコールドスタートの合計時間が5秒に短縮されました。

GPUメモリスナップショットの利用は非常に簡単でclsの引数に`experimental_options={"enable_gpu_snapshot": True}`を含めるだけです。なお、ここにCPUスナップショットの設定`snap=True`は不要で自動的にスナップショットが精鋭されます。
